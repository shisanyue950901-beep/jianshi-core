## 中文化规则

用户可见内容默认中文优先。能自然中文表达的概念全部中文化；只有官方平台名和确有检索价值的行业缩写保留在中文后。

例如：
- 软件订阅服务（SaaS）
- 亚马逊物流（FBA）
- 亚马逊按需印刷（Amazon Merch）
- 无货源代发（Dropshipping）
- 邮件订阅媒体（Newsletter）

工程内部变量、Slug、数据库字段可以继续保留英文，不对用户展示。

## 1. 产品主线

见势当前只做：

> **海外已验证的一人公司 / 小团队项目 → 筛选 → 中文解释 → 推荐给中国用户。**

本阶段不做新数据源、不做平台路线扩展、不做内容创作者体系。

## 2. 为什么先做候选池

不能继续“看到一个数据类型就做一个页面”。

正确顺序是：

```
海外真实项目
→ 主业务类型去重
→ 一人/小团队适配初筛
→ 中国用户参考价值
→ 决定是否值得进入详情页
```

## 3. 证据口径

当前候选池的直接商业样本来自同一商业来源。

因此：

```
SAMPLE_COUNT != SOURCE_DIVERSITY
```

本阶段优先按 `public_title` 的主业务类型计数，而不是简单看 monetizations。

原因：

一条 listing 可能同时拥有：

- SaaS
- Subscription
- Service

如果直接按 monetization 分类，同一项目会被重复当成多个不同项目。

因此 P4.7A 使用：

> **主业务类型优先 + listing 去重**

## 4. 一人公司标签的边界

当前来源并没有可靠的“团队人数”字段。

即使 listing 展示每周运营工时，也不能证明项目一定由一个人运营。

所以：

> **“一人/小团队适配”是见势编辑筛选，不是来源事实。**

以后页面必须明确区分：

- 海外真实商业事实；
- 见势对中国个人创业者的适配判断。

## 6. 为什么不是按样本数排序

Amazon FBA 有很多商业样本，但不代表它自动最适合中国个人创业者。

见势推荐还需要考虑：

- 启动资金；
- 库存；
- 平台依赖；
- 合规；
- 产品复杂度；
- 是否可以小规模验证；
- 是否适合个人先启动。

同样，Newsletter 当前只有 1 个严格主业务样本，所以即使理论上很适合个人，也只能先“继续观察”。

不会把产品再次变成“全是 AI / 全是内容 / 全是电商”。

## 8. 特别说明：YouTube

YouTube 在这里仅仅是 **一个已经有真实商业样本的项目类型**。

它不再被提升成“内容创作者主线”。

见势会问：

> 这种海外频道资产的商业结构是否值得中国用户研究？

而不是：

> 所有中国用户是不是都应该去做 YouTube？
