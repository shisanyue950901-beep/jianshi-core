## 2. 测试矩阵

单元：状态机、内容元数据、媒体权属、路径规范、输入超长与非法类型。
集成：CMS → public projection；业务 API → RLS → 审核日志；课程 → 存储授权。
安全：两企业/两创作者 A/B，水平越权、未登录、管理员越权、XSS、CSRF、IDOR、重放/重复提交、频率限制、删除/撤回、私有日志泄漏。
UI：360/390/768/1024/1440 响应式、键盘导航、Esc、图像缺失、筛选重置、骨架/空状态；减少动态效果。
部署：原 GitHub CI；CF_PAGES=1 真实构建保护；Cloudflare Pages 部署状态；最终域名主要 URL 200、菜单与表单点击；缓存及旧链接。
数据：自动化测试仅合成数据，生产字段白名单扫描；绝不绕过既有私有研究许可和 cron 合同。

## 3. 严格生产发布顺序

1. 在独立 Git 分支开发，限定范围与允许文件；禁止直接改 web/dist/、public/、dist/ 生成物。
2. PR 自动测试与 code review；内容/权限更改需要专门审核，不以合并权限代替业务审批。
3. 合并后 GitHub main 构建；确认最终静态快照 commit SHA 与源一致。
4. Cloudflare Pages 及 Workers 实际部署 SUCCESS，确认正式域名路由而非旧部署缓存。
5. 验收每个新增路径的 HTTP 状态、标题、核心 CTA，旧 /projects/ 与 /research/ 可用。
6. 记录含提交 SHA、PR、CI、部署、截图/回归、阻断项、回滚入口的中文报告。

## 4. 回滚及失败关闭

静态站：保留上一通过的完整构建制品与发布 SHA，部署失败/线上 404 立即停止扩范围，可重部署上一版并核对旧链接。
数据库：备份/前向修复脚本先在 staging 演练；有实际客户数据时禁止简单 DROP 回滚。只有单独审批才对 production 施加迁移。
认证或私有接口失效：关闭业务功能开关、拒绝提交，保护用户数据；不得通过放宽 RLS 或把 service_role 放浏览器应急。
个人信息泄漏：立即暂停相应页面，撤回缓存、审计受影响范围、按要求处置。

本轮只做 G0 六份合同与 G1 第一段（离线 CMS 内容验证和 UI 令牌），不部署数据库，不接通真实订单、企业认证、课程支付或生产登录。不改变 UTC 四个 cron 槽、HN7/RSS1/GitHub2 限额。
